PLC Telemetry & Fault Analytics

A Raspberry Pi bridge that polls PLC tags over Pycomm3 and lands cycle-time and fault data in Power BI — turning a floor that ran on guesswork into one with real-time visibility.

RoleDesigned & built end to end
StackPython, Pycomm3, Raspberry Pi, Power BI
SourceAllen-Bradley PLC tags
OutputReal-time cycle & fault analytics

The problem

The PLCs already knew everything worth knowing — cycle times, fault codes, state transitions — but none of it left the controller. Downtime got reconstructed after the fact from operator recollection, and improvement work was argued from anecdote instead of data. There was no way to answer "which fault is actually costing us the most hours this month" without someone standing at the machine with a clipboard.

Architecture

A Raspberry Pi sits on the plant network and polls PLC tags over EtherNet/IP using Pycomm3. It is a read-only bridge by design — it never writes to the controller, so it cannot affect the process it is measuring, which is the property that made it acceptable to put on production equipment at all.

Polling design. Tags are polled at a rate matched to what they actually represent — a cycle timer and a fault word do not need the same interval, and over-polling a controller on a production network is a good way to get your project switched off.

Event extraction. Raw tag values are not analytics. The poller turns tag transitions into discrete events with durations, which is what makes a fault Pareto or a cycle-time distribution possible downstream.

Result

The floor got real-time visibility into cycle times and fault analytics, which changed what improvement conversations could be about. The die transfer optimization on the weld cell project is a direct consequence — the 1.7-second transfer was identifiable as the constraint because the pipeline was measuring it.
