Paint Allocation
& Floor Runlists

A planning tool that models routing and BOM as a single directed graph, allocates painted stock against ship-date FIFO, and publishes a runlist the floor works from. It replaced an Excel workflow that took a planner most of a shift.

The problem

Planning paint meant holding four things in your head at once. A planner kept a “hot parts” sheet in Excel, transcribed by hand into a second Excel workbook, then went hunting for the actual containers — first through Plex, across separate Demand, Inventory and Subcomponents screens, then physically on the floor — and twice over, because the material moves across a site boundary before it is finished.

The structural problem underneath: a painted part cannot run until every painted sub-component it depends on has run. That dependency lives in the BOM, but nothing put it next to on-hand inventory and open demand at the same time. So the planner re-derived it by hand, every shift, from three screens that never agreed on when they were last refreshed.

It is harder than one plant's scheduling problem because the graph crosses a company boundary. P6 is both a supplier and a customer — material arrives from them and finished goods go back to them — so a dependency chain can leave the site, come back, and still gate a release. The planner was tracking inventory on both sides of that boundary in separate screens.

It cost what you would expect — rushed jobs and missed deadlines — and it cost most on the shifts where the floor deviated from plan, which is precisely when re-deriving it by hand is slowest.

The planner now looks at two things: the tool, and the floor. The Demand / Inventory / Subcomponents round trip is gone, and so is the second Excel workbook — the runlist the floor works from is published straight out of the allocation the planner just approved.

The floor view is a runlist in the terms the floor actually uses: part number, quantity, colour, container serial and location, including how many parts to take from each container. Not a plan to interpret — a list to work.

Approach

Three attempts, and the third one retreated. The first iterations were in Excel — naive, and they did not survive contact with the real BOM depth. The second was a VBA script that still took too long to run, and leaned on Power Automate to scrape the data out of the ERP through browser automation. That last part was the problem: browser automation against an ERP UI is a dependency on someone else's markup not changing, and it was not reliable enough to plan a shift around.

So the current tool deliberately gave that up. It reads Plex reports the planner exports into a folder tree — a manual step, and the honest rough edge in the system. But a manual export that always works beats an automated pull that fails on the shift you needed it most, and moving the complexity out of data acquisition left it available for the part that actually earns it.

One graph, not two data structures. Routing and BOM are usually held separately and reconciled by a human. graph_allocator_V2 models both as a single directed graph: nodes are (part, operation) pairs from the process routings, routing edges join consecutive operations of a part, and component edges join a parent operation to the components consumed at it, quantity-scaled from the exploded BOM. On-hand containers attach to the node they are sitting at. The BOM is asserted to be a DAG, so the walk terminates.

Once it is one graph, “what can run now” stops being a question the planner re-derives and becomes a traversal. Each release walks upstream from its part's final operation, consuming on-hand stock at each step and exploding whatever demand is left into painted sub-components as internal releases, stopping when the demand is met or the routing runs out.

FIFO because old stock costs twice. Releases are processed in ship-date FIFO order, and the reason is a process constraint rather than an administrative preference. Bare steel sitting in inventory oxidises, so material ages toward scrap. It also gathers dust — and in a coating process that is not cosmetic, it is time: every dusty part needs surface cleaning before it can run, and a part that skips it risks contaminating the baths, which is a problem for everything painted after it. Clearing the oldest material first avoids both, so the scheduling rule is really a contamination-control rule.

When a push exceeds a release's balance, the surplus cascades to later releases of the same part rather than being dropped — FIFO all the way down, so nothing falls out of the plan silently.

Refusing to allocate is most of the logic. Only Ecoat and Powdercoat material is allocated; rework and MRB containers are set aside and never allocated at all. A push only takes containers still upstream of the target paint operation, so the tool cannot schedule a repaint, and anything ineligible is reported as skipped rather than quietly omitted. A Powdercoat push that exceeds available e-coated feedstock auto-adds the EC items it implies, flagged amber for the planner to acknowledge — the tool surfaces the dependency instead of allowing a run that would stall.

Two audiences, two trust models. The planner dashboard is strictly read-only over ERP data — it re-runs the pipeline in memory and writes only its own derived files. The floor view reads one published runlist_live.json. Exactly one planner instance holds a write lock, enforced by heartbeat; every other instance, planner or floor, is a read-only consumer. That constraint came from experience: an earlier design allowed shared writable state and produced conflicts, so the rebuild kept shared state but reduced it to a single writer.

Suggests, does not decide. The engine proposes; the planner selects, adjusts quantities and publishes. Coverage is shown per release — past-paint, paintable, pipeline or short — so the planner can see why something is ranked where it is. A scheduler that overrides the person who can see the floor gets switched off in a week; one that hides its reasoning never gets trusted at all.

Where it stands

The system runs entirely locally — PyInstaller executables on 127.0.0.1, no service and no database — and reads Plex reports exported into a shared folder tree. It is versioned on SemVer and currently at V2.2.2, having grown from a read-only dashboard through the floor runlist build to features like overdue detection and inventory-age warnings.

I architected the system and built the allocation engine, working from feedback with the planners and production managers who use it. The front end was built with AI assistance; I have no frontend background, and the interface was not the part of this problem worth learning on.

That feedback loop is also why iterating on a live line was practical — the people who would catch a wrong answer fastest were the ones sitting next to me while it was built.

It was validated in production, which the architecture made safe. There is no automated test suite; the tool was tested by running it against live data with the planners who use it. That is defensible here specifically because the allocation view is read-only over ERP data — the worst case for a wrong answer is a suggestion the planner rejects, not a corrupted record. The trust model was chosen for other reasons, but it is what kept that approach reasonable.

It is documented for handoff rather than for show: the repository carries a behaviour spec, a build log and an IT-facing README explicit about the rough edges. The manual ERP export is a choice — the automated alternative was tried, depended on browser automation, and was less reliable than the person doing it by hand. The missing test suite is a genuine gap: production testing proves the behaviour today, but it gives whoever inherits this no safety net against regressions tomorrow. That is the first thing I would add if it outgrew being an internal tool.
